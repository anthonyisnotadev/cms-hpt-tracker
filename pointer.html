The pointer file

/cms-hpt.txt gives hospitals one predictable place to identify the price page, the direct machine-readable file, and a contact for that publication.

Rule 45 CFR 180.50(d)(6)
Required Since Jan. 2024
Format Plain text

Purpose

A stable signpost for a moving target

Hospital price files can live on a hospital website, a health-system site, a storage service, or a vendor platform. The pointer tells software which file the hospital identifies as its publication.

Before the pointer requirement, locating an MRF often meant searching menus, scanning a price-transparency page, or guessing filenames. Those approaches are difficult to automate and can confuse a patient estimator, an insurer file, or an old download with the comprehensive hospital MRF.

The pointer separates discovery from storage. The hospital maintains a predictable text file on the selected public website, while the much larger MRF can live at a different URL. If the MRF moves, the pointer can be updated without changing the standard place where software starts.

Pointer

/cms-hpt.txt

A small plain-text directory that identifies the location, source page, direct MRF URL, and contact.

Source page

Human-readable webpage

The public price-transparency page where the hospital presents or links to the MRF.

MRF

Full price data

The CSV or JSON download containing the hospital's standard charges.

Location

The path is simple on purpose

The selected website places the file in its root folder, producing an address such as https://hospital.example/cms-hpt.txt.

The root location matters because it can be checked without knowing the site's navigation, content-management system, or URL structure. It is similar in spirit to other well-known text files used by websites, but cms-hpt.txt has its own CMS-defined purpose and format.

The regulation also requires a separate website footer link labeled “Price Transparency.” That link goes to the public source page that hosts the MRF link. The footer link helps people find the page, while the pointer gives software a structured route to the file.

The pointer is not the MRF

A working cms-hpt.txt can still lead to a broken, blocked, stale, or outdated MRF. A valid audit follows the pointer and checks the listed file rather than stopping at the text response.

Format

Five labeled fields make one entry

The regulation describes four required pieces of information. The CMS text format represents the point of contact as separate name and email fields, producing five labeled lines for a location.

location-name
The hospital or campus whose charges are represented. A specific location name helps connect a system-level pointer to the correct facility.
source-page-url
The public webpage that presents the hospital's price-transparency information and hosts the link to the MRF.
mrf-url
A direct link to the comprehensive CSV or JSON file. It should lead to the file itself rather than a general webpage or search tool.
contact-name
The hospital point of contact responsible for questions about the publication. This may be a role or team rather than a person.
contact-email
An email address for the point of contact.

Entries are separated by blank lines when a pointer describes more than one location. The text is deliberately lightweight, so a browser, command-line tool, or crawler can read it without running JavaScript.

Hospitals and systems

One domain may represent many locations

A health system can maintain one pointer containing separate entries for hospitals and campuses published through the same website.

Different locations may point to different MRFs. Locations can also point to the same MRF when that file genuinely covers them. The location name in each entry is important because a health-system brand alone may not identify the individual hospital in the federal roster.

The MRF does not have to be stored on the same domain as the pointer. A hospital may use a vendor or file-hosting service for the large download. In that case, the pointer on the selected hospital or system website remains the declaration that connects the location to the external file.

A shared domain is useful evidence of organizational context, but it is not enough by itself to prove that every hospital in a system is covered. The location entry and the identity information inside the MRF are needed to make that connection.

Common problems

A short file can still fail in several ways

Missing at the root

The website works, but the standard /cms-hpt.txt path returns a not-found page or another unrelated response.

HTML instead of text

A security page, site template, or redirect response is returned where the pointer content should be.

Hospital not listed

A system pointer opens, but no entry can be matched confidently to the hospital being checked.

MRF URL omitted or indirect

The entry lacks a usable mrf-url, or it links to a webpage instead of a direct CSV or JSON download.

Link no longer works

The pointer exists, but the listed MRF has moved, expired, or returns an error.

Automation refused

The server allows ordinary browsing but rejects the automated request used for a reproducible audit.

Names also vary. A pointer might use a campus name, legal entity, shortened brand, or all-capitals label while the roster uses something else. The tracker uses names as evidence, but avoids forcing an uncertain match just because two facilities share a domain.

This tracker

The pointer creates a reproducible audit path

The normal check moves from a known hospital domain to a location-specific pointer entry, then to the MRF named by that entry.

1. Request

Open /cms-hpt.txt on the known public domain and record the response.

2. Parse

Read the labeled fields and separate multiple location entries.

3. Match

Connect an entry to a hospital only when the available identity evidence supports that match.

4. Follow

Request the declared MRF URL and read a bounded portion of the file rather than downloading the entire data set.

5. Record

Save the observed access result, template version, update date, and evidence needed to review the finding.

A refusal to serve an automated request is recorded as blocked, not treated as proof that the file is missing. If no usable hospital website is known, or a system pointer cannot be matched to a specific hospital, the record remains not assessed. Keeping those outcomes separate makes the limits of the audit visible.

The project also preserves reviewed evidence from direct MRF links when the standard pointer path is unavailable. That evidence is labeled by how it was obtained, and a file header must support the facility match. A shared health-system source is not treated as proof on its own.

Contact privacy

The archive keeps the evidence without publishing easy-to-search contacts

Hospital pointer files are public, but their contact names and email addresses are not needed for the public tracker interface.

The repository retains pointer text for reproducibility and review. Before that archive is stored, values in contact-name and contact-email are obfuscated. The project key is included with the code because this is protection against casual plaintext indexing, not encryption intended to keep the fields secret.

Local npm workflows can decode the contact fields when a maintainer needs to review a source or prepare outreach. The generated public tracker data does not expose those contact fields, and the archived pointer directory is not part of the hosted site artifact.
